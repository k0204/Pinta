## 修复图层预览弹窗（Ctrl+左键）非等比缩放

- 文件：`Pinta.Gui.Widgets/Widgets/Layers/LayerPreviewWindow.cs`
- 根因：`preview_area`（Gtk.Overlay）直接作为 `Gtk.ScrolledWindow` 的子控件时，GTK4 会用 GtkViewport 包裹并把子控件拉伸到**至少视口大小**。缩小到小于视口时 overlay 被拉伸，`Gtk.Picture` 的 `ContentFit.Fill` 随之把图像拉成视口宽高比 → 变形。放大超过视口时分配==请求，所以看起来正常，导致"缩放逻辑不对"的表象。
- 修复：overlay 外层包一个 `Gtk.Box` 作为滚动子控件；overlay 设 `Hexpand/Vexpand=true` + `Halign/Valign=Center`。这样 overlay 始终按 `SetSizeRequest` 请求的等比尺寸分配并居中，不再被视口拉伸。
- 要点：GTK4 中 expand=true + align=Center 的组合表示"拿满槽位空间、内容按 natural 尺寸居中"，是视口内居中控件的标准写法。
- 验证：无残留 Pinta 进程；`dotnet build Pinta.Gui.Widgets -c Release` 通过。

## 预览窗口打开时视图居中

- 需求：窗口打开时显示图像中心，而不是左上角。
- v1：在 Configure 的 IdleAdd 里调 CenterView()。风险：Windows 上 GTK4 帧时钟/布局可能晚于 idle 执行，滚动条 Upper 还没配置 → 居中静默失败（停在左上角）。
- v2（最终）：改为 `CenterViewWhenReady()` —— 订阅 H/V 两个 `Gtk.Adjustment.OnChanged`，当 `Upper>1`（布局已配置边界）后居中一次并退订；订阅后立即调用一次以覆盖"已就绪"情况。无时序竞态，确定性。
- 居中公式：`SetAdjustmentValue(adj, (adj.Upper - adj.PageSize) / 2)`，复用已有的 clamp 逻辑；内容小于视口时自然落到 0（由 Box 包裹居中）。
- 运行方式：用户约定直接用 `./run.bat`（= dev.ps1 -Run，Debug 构建到 build/bin 后启动 Pinta）。
- 环境注意：`Pinta.Resources\bin\Release\net10.0\icons\...` 的 PNG 曾被未知进程锁定导致 Release 构建 MSB3021 失败（Access denied）；Debug 构建到 build/bin 不受影响。构建前按 AGENTS.md 先停 Pinta/.NET 进程。

## v4（当前）：调整值对象接错——改为从自动 viewport 取

- 用户第三次反馈打开仍左上角。v3 逻辑（TryCenterViewOnce + 多路触发）理论上正确但实际不生效。
- 真正根因：`Gtk.ScrolledWindow` 对非 scrollable 子控件会**自动包一个 Gtk.Viewport**，该 viewport 用的是自己创建的 Gtk.Adjustment（`gtk_viewport_new(priv->hadjustment, priv->vadjustment)`——若 priv->hadjustment 此时为 NULL，则 viewport 自行创建，scrolled window 的 priv 保持 NULL）。之后 `scrolled_window.Hadjustment` getter 是懒构造的——会创建一个**全新的、独立的** adjustment 存进 priv，但这个对象**从未与 viewport 关联**，viewport 继续用自己那套。因此 `scrolled_window.Hadjustment` 在"非 scrollable 子+自动 viewport"场景下返回的是**死对象**：
  - 订阅 `OnChanged` 从不触发（无人 configure 这个对象）。
  - `PageSize` 永远 0，居中条件 `PageSize > 0` 永不满足。
  - `SetScale` 写入死对象，缩放时滚动条不动（用户说的"缩放后居中"实际只是缩小到 < 视口时 Box 包裹的视觉居中）。
  - 拖拽平移同理不生效。
- 修复（参照 `CanvasWindow.cs` / `DocumentWorkspace.cs` 的成熟模式）：添加 `RealHorizontal`/`RealVertical` 两个属性，从 `scrolled_window.Child`（自动 viewport）调用 `GetHadjustment()`/`GetVadjustment()` 拿到真正被配置的 adjustment。替换全部 10 处 `scrolled_window.Hadjustment!`/`Vadjustment!` 引用（含 SetScale 与 HandlePanBegin/Update）。
- 启示：在 GTK4 中，`GtkScrolledWindow.Hadjustment` 对**非 scrollable 子（自动 viewport）**不可靠，对**显式 scrollable 子（如 Gtk.Viewport）**才等价于子自己的 adjustment。需要直接拿子（viewport）的 adjustment。

## v5（当前）：一次性标志 → 持续居中直到用户交互

- 用户第四次反馈：打开仍不居中，但移动/缩放后就居中了。说明 v4 的 `RealHorizontal/Vertical` 修复生效（交互时写入能改变 scroll），但**打开时的首次居中没成功**。
- 根因：v4 用 `view_centered` 一次性标志——首次 `OnChanged`（PageSize>0）时居中并设 true。但**首次 OnChanged 的 PageSize 可能是窗口未最终确定尺寸时的临时值**，居中到错误位置；之后窗口尺寸确定、PageSize 变为最终值、OnChanged 再次触发——但 `view_centered` 已 true，不再居中。用户交互（缩放/移动）触发了**重新布局** → OnChanged 再次触发 → 此时 view_centered 仍是 false（因为之前的 OnChanged PageSize=0 没设 true）→ 居中成功。
- 修复：把 `view_centered`（一次性）改为 `user_interacted`（语义反转）——**用户交互前每次 OnChanged 都重新居中**（即使首次 PageSize 是临时值，后续 PageSize 确定后也会重新居中到正确值）；用户一旦滚轮缩放/拖拽平移/键盘缩放就设 `user_interacted = true`，之后不再自动居中，保留用户位置。
- 改动点：字段 `view_centered` → `user_interacted`；`TryCenterViewOnce` → `CenterView`（去掉一次性检查）；OnChanged handler 加 `if (!user_interacted)` 守卫；HandleScroll/HandlePanBegin/HandleKeyPressed 设 `user_interacted = true`。
